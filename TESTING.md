# Проверка релиза

Документ описывает обязательную проверку текущей версии перед публикацией образа и обновлением рабочего бота.

## Автоматические проверки

```bash
python -m pip install -r requirements-dev.txt
python -m compileall -q app tests
python -c "from pathlib import Path; import yaml; [yaml.safe_load(path.read_text(encoding='utf-8')) for path in Path('.').rglob('*.yml')]"
pytest -q
```

Workflow `Publish GHCR image` выполняет эти проверки до сборки и публикации multi-arch образа. При ошибке тестов образ не публикуется.

## Обновление существующей установки

1. Создать резервную копию `/data/bot.db`.
2. Обновить и пересоздать контейнер.
3. Проверить `/health` и вход в `http://IP_ZIMAOS:18080/admin`.
4. Убедиться, что старые заявки, формы, тарифы, услуги и занятость сохранены.
5. Проверить журнал контейнера на ошибки миграции SQLite.

## Telegram и игра

- В обычном личном чате с ботом `/start` показывает кнопку игры.
- `/game` открывает поле 3×3; проверяются ходы, победа, ничья и новая игра.
- В Telegram Business-чате игра не запускается и не создаёт CRM-заявку.
- `/test` использует реальные формы и занятость, но не сохраняет заявку.

## Залы и анкета

- Задать первому залу вместимость 300, второму — 120 гостей.
- При ответе `150–250` первый зал должен быть доступен, второй показан с `❌`.
- Неподходящий зал нельзя выбрать кнопкой или ручным вводом.
- Условный вопрос появляется только при выполнении заданного условия.
- Скрытый обязательный вопрос не блокирует отправку анкеты.

## Бронирование

- Прошедшие даты запрещены.
- Понедельник корректно обрабатывается как `weekday=0`.
- Начало доступно только при наличии хотя бы одного допустимого окончания.
- Причина недоступности учитывает правила, повторяющуюся занятость, буферы и существующие брони.
- Ночная бронь, например `21:00–05:00`, блокирует обе календарные даты.
- Разные залы можно забронировать на одно время; один зал — нельзя.
- Hold создаётся один раз и ограничивается rate limit.

## Услуги, ресурсы и деньги

- Количество услуги пересчитывает итоговую стоимость.
- Остаток оборудования учитывает пересекающиеся мероприятия.
- Остаток повторно проверяется перед сохранением заявки.
- Частичные платежи суммируются; повторный webhook не удваивает сумму.
- В тестовом магазине YooKassa проверяются дедлайн предоплаты и возврат.

## Режимы эксплуатации

- `STAGING_MODE=1` не создаёт реальную CRM-заявку.
- Антиспам ограничивает серию частых Business-сообщений.
- Web Admin проверяется под ролями `owner`, `manager` и `viewer`.
- Клиентское время соответствует `TZ`, служебные timestamps остаются в UTC.
